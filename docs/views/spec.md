Nothing here is built; its fifteen open questions are all ruled: #1 to #9 on 2026-11-08, #6, #8 and #9 against their recommendations and the rest as recommended, with #14 added and ruled the same day; #10, #11 and #13 on 2026-11-09 as recommended and #12 against its recommendation, with #15 added and ruled that day, taking the board out; its review ([`views-spec.md`](../../../reviews-issue/views-spec.md)) was folded on 2026-11-09; and its plan is [`plan.md`](plan.md), whose own review of 2026-11-09 corrected five points here, the draft's key, the terms the box refuses, the chip click, a comparison on an empty cell and the header's minimum, and added three by the owner's rulings of that day: several bare words, `has:` and `no:` on a live-toggle column, and the page size. The plan's issues are [#586](https://github.com/Jde-cpp/opc-hub/issues/586) and its phases, #587 to #597. Line numbers cite opc-hub2 at `3cce6fef`, branch `process`, since merged to main as `f267753f`; the alarms page main added afterwards ([#426](https://github.com/Jde-cpp/opc-hub/issues/426)) is named without a line.

## Overview

Most of the site is a list: the users, groups, roles and resources under Access, a gateway's connections, templates and historian groups, a node's children, a gateway's watch list, an application server's logs, and the pick lists on a record's tabs. Every one of them runs on the same machinery. A `View` is the columns shown and their order, the sort, the filters and a page size ([`view.ts:192`](../../web/framework/control/src/lib/model/ql/view.ts#L192)); a `ViewSet` holds a list's built-in views, the user's saved ones and at most one unsaved twin ([`view-set.ts:17`](../../web/framework/control/src/lib/model/ql/view-set.ts#L17)); the `ViewToolbar` shows them as a toggle group in the middle of the bar, with a tune button beside it ([`view-toolbar.html:22`](../../web/framework/control/src/lib/shared/view-toolbar/view-toolbar.html#L22)); and the tune button replaces the whole list with an editor of three tabs, Filter, Display and Sort, whose Save, Show, Delete and Cancel are the only way to change anything but the sort ([`ql-list-settings.html:8`](../../web/framework/control/src/lib/pages/ql/list/ql-list-settings/ql-list-settings.html#L8)). The one shortcut is a header click, which re-sorts at once and makes the twin ([`ql-list.ts:80`](../../web/framework/control/src/lib/pages/ql/list/ql-list.ts#L80)). The saved views are per user, in the AppServer's `profiles` table ([`access-meta.jsonnet:203`](../../libs/access/config/access-meta.jsonnet#L203)); the current view's index is per browser ([`local-prefs.ts:30`](../../web/spa/control/src/lib/services/profile/local-prefs.ts#L30)).

A GitHub Projects view is the same idea with a different face, and the face is the point. The views are tabs across the top of the page, each with a layout, and a `+ New view` after them. Under the tabs sits a filter box that takes a query, `status:done -assignee:@me label:bug,support`, with suggestions as you type. Every change, a filter typed, a column hidden, dragged or resized, a sort picked from the column's menu, a group or a slice chosen, applies at once and puts a dot on the tab for the unsaved change; `Save` keeps it, `Discard` returns to the saved view, and until then the change is yours alone, in the url, so a reload keeps it and a pasted link carries it. The column header has a menu, sort, group, slice, hide. A grouped table has a header row per group with its count and the sums of its number fields. A slice panel on the left lists one field's values with their counts, and a click narrows the view to one. The same view can be a table, a board whose columns are one field's values, or a roadmap. Clicking an item opens it in a side panel, and the table is a keyboard grid: arrows between cells, Enter to open, Shift+Space to select.

This spec takes that face for every list in the site, rendered in the site's own Material theme rather than GitHub's: Projects' shapes, controls and behaviour, the site's type, colour and density. It is two parts. **The view bar** replaces the toggle group and the full-page editor: a tabs row, a filter box with a query syntax, a view menu, header menus, and `Save`/`Discard` over a draft kept in the browser. **Grouping and slicing** add what the lists never had, which the QL supports once it can count by a field. Projects' board and roadmap layouts are not taken, so every view is a table (*Open questions* #11, #15). Projects' item panel is not taken: a row opens the record's page as it does now, and a pane across the bottom of the list can come later, under [#256](https://github.com/Jde-cpp/opc-hub/issues/256) (*Open questions* #8). Every host of a `ViewSet`, the GraphQL lists, the logs, a node's children and the watch list, gets all of it through the one toolbar, with the filter compiled once and run either as a QL argument list or as a predicate over rows already in the browser, which is how those two kinds of host already differ ([`node-view.ts:9`](../../web/opc/control/src/lib/model/node-view.ts#L9)). `Field sum` is empty on a node's children, where no column is always a number. The logs take the tabs, `Fields`, the sort and the draft alone: their rows are a window of a paged log, so a filter, a group or a slice over them would be wrong, and a search of the whole log is work of its own ([#584](https://github.com/Jde-cpp/opc-hub/issues/584)). The alarms page is left out for now (*Hosts*).

## Design

**The view bar.** Two rows above the table. The first is the tabs row: one `mat-tab-nav-bar` tab per view, with one `mat-tab-nav-panel` holding the table, the user's saved views in their order or, while they have saved none, the route's built-in ones, labelled with the view's name, a small primary-coloured dot after the name while the view has a draft, and a `+ New view` text button after the last tab, which makes a copy of the current view named *View N* after its number, saves it as the user's and selects it. The active tab carries a chevron button inside its link that opens the view menu, an AXE `nested-interactive` failure accepted by the owner's ruling of 2026-11-09, with the button's click and keydown stopped from reaching the tab's own handlers, in Projects' order less its `Layout`: `Fields`, `Group by`, `Sort by`, `Slice by` and `Field sum`, each a submenu, `Page size` on a list that pages, then `Rename`, `Duplicate`, `Save changes`, `Discard changes` and `Delete`. `Page size` is the site's own entry, ruled 2026-11-09 on the plan's review: a submenu of 10, 25, 50, 100, 250 and 500 rows, and the view's own number where it is none of those. The Display tab set the size, and the pager, which has a box for it, is absent while a list fits one page ([`ql-list.html:27`](../../web/framework/control/src/lib/pages/ql/list/ql-list.html#L27)). `Rename` edits the tab's label in place, Enter commits, Escape reverts. A name need not be unique: two tabs may read the same, as in Projects, and neither `Rename` nor `Duplicate` refuses one; a duplicate keeps its original's name and sits after it (*Open questions* #14). What tells views apart is a number each carries, the route's views 1 to n in the route's order and a new or duplicated view the next above the set's highest. The route's built-in views are a starting set, shown only while the user has saved no views of their own for the list: the first thing saved, a change, a rename, a duplicate, a deletion, a new view or a new order, writes the whole set to the user's profile, the built-in ones included, and from then every tab is the user's, renamed, duplicated, saved over and deleted alike, and the route's are not read (*Persistence*). Deleting the last tab leaves none saved, so the built-in views show again; that is the one way back to them, and there is no reset entry. Tabs are dragged into order with CDK drag-drop, or moved with `Move left` and `Move right` in the view menu, and the order is saved with the views. The second row is the list toolbar as it is ([`_general.scss:101`](../../web/spa/control/src/styles/_general.scss#L101)), its zones re-let: the host's own controls stay left, `Add` first; the centre is the filter box, taking the width the zones leave it; `Discard` and `Save` appear at its right end while a draft exists; the right zone is Refresh, the host's right-hand controls, and the row count. On a phone the filter box takes a row of its own under the other two zones, as the centre zone does today ([`_general.scss:154`](../../web/spa/control/src/styles/_general.scss#L154)), after them in the tab order. The full-page editor and its three tabs go; the tune button goes with it.

**The draft.** `ViewSet.show` ([`view-set.ts:41`](../../web/framework/control/src/lib/model/ql/view-set.ts#L41)) already makes an unsaved twin and `save` ([`:64`](../../web/framework/control/src/lib/model/ql/view-set.ts#L64)) promotes it; the draft is that twin, made by every control rather than by `Show`. `View.copy` today shares its `ViewField` objects and their `Style` with the view it copies ([`view.ts:216`](../../web/framework/control/src/lib/model/ql/view.ts#L216), [`:116`](../../web/framework/control/src/lib/model/ql/view.ts#L116)), so a hide or a resize would reach the saved view; it copies each field and its style instead, and `deletedView`, which finds its column in the copy by identity ([`ql-list-resolver.ts:175`](../../web/framework/control/src/lib/services/ql-list-resolver.ts#L175)), compares by name. A change to the filter, the fields, their order or widths, the sort, the page size, the group, the slice field or the sums replaces the current view with its twin changed, the host re-queries or re-applies as it does for a header sort today ([`ql-list.ts:80`](../../web/framework/control/src/lib/pages/ql/list/ql-list.ts#L80)), and the tab shows its dot. `Save` writes the twin over its view, and on a built-in view saves the whole set as the user's with that view changed; `Discard` drops the twin and shows the saved view again. Switching tabs keeps the draft of the tab left, one per view at most, so a user can compare two views half-edited and come back; today's rule, that switching away discards the twin ([`view-set.ts:17`](../../web/framework/control/src/lib/model/ql/view-set.ts#L17)), goes. Every draft of a list is written on each change to `LocalPrefs` ([`local-prefs.ts:6`](../../web/spa/control/src/lib/services/profile/local-prefs.ts#L6)) under the user's key and the `ViewSet`'s key ([`view-set.ts:10`](../../web/framework/control/src/lib/model/ql/view-set.ts#L10)), since `LocalPrefs` names no user ([`local-prefs.ts:33`](../../web/spa/control/src/lib/services/profile/local-prefs.ts#L33)) and a station may be shared, as the record a saved view writes with its view's number, and the `ViewSet` reads them back when it is built. The url's query string is not used: two lists on one url cannot collide, nothing navigates, so no resolver re-runs, and a reload or a return from a record's page rebuilds every tab's draft, widths and sums included. A draft stays in the browser it was made in until it is saved, and a link does not carry it; sharing waits for shared views (*Open questions* #10). The selected tab is still remembered per browser ([`local-prefs.ts:30`](../../web/spa/control/src/lib/services/profile/local-prefs.ts#L30)), by the view's number rather than its place, since tabs reorder and names repeat. A collapsed group and the slice value chosen are state of the moment, kept in the browser beside the drafts, never saved.

**The filter box.** An outlined `mat-form-field` with a `filter_list` prefix and the placeholder *Filter by keyword or by field*, holding plain text, not chips. Its grammar is Projects', cut to what the columns are, so it has no `@me`, since no list has a column that keys `users`:

| Term | Means | Compiled to |
| --- | --- | --- |
| `field:a` | the column equals `a` | `field:[a]`, the QL's `in` ([`view.ts:381`](../../web/framework/control/src/lib/model/ql/view.ts#L381)) |
| `field:a,b` | either | `field:[a,b]` |
| `-field:a,b` | neither, a null cell included; `has:field` beside it leaves nulls out | `{nin:[a,b]}`, which gains `or x is null` on a nullable column ([`WhereClause.cpp:94`](../../libs/db/src/generators/WhereClause.cpp#L94)); `{nin:[a,null]}` still excludes nulls |
| `no:field`, `has:field` | the column is null, is not | `field:[null]`, `{ne:null}` ([`view.ts:362`](../../web/framework/control/src/lib/model/ql/view.ts#L362)) |
| `field:>3`, `>=`, `<`, `<=` | a comparison, on numbers and dates | `{gt:3}` and the rest ([`view.ts:317`](../../web/framework/control/src/lib/model/ql/view.ts#L317)) |
| `field:a..b`, `*..b`, `a..*` | an inclusive range | `{gte:a,lte:b}`, a two-key object, one clause per key ([`WhereClauseTests.cpp:73`](../../libs/ql/tests/WhereClauseTests.cpp#L73)); on a date column, whole days as below |
| `@today`, `@today-7d`, `@today+1d` | a date relative to the day, re-read at each query | `Days` ([`view.ts:9`](../../web/framework/control/src/lib/model/ql/view.ts#L9)), kept as it is |
| `"a b"`, `'a b'` | a value with a space or a comma | the value |
| `word` | a bare word: on a GraphQL list the name contains it, with case as the database compares it; on the node and watch lists any text cell contains it, whatever its case; several bare words must all match | `name:{glob:"*word*"}` ([`FilterQL.cpp:22`](../../libs/ql/src/types/FilterQL.cpp#L22), [`Syntax.h:12`](../../include/jde/db/generators/Syntax.h#L12)), a typed `*`, `?` or `[` written as a one-character class; several words are a list, `name:{glob:["*pump*","*station*"]}`; *Open questions* #7 |

A field is named as its header reads, case-insensitive, quoted when it has a space, `"security mode":Sign`; the QL name is accepted too. Repeating a field ands its terms; or between fields is not offered. On the GraphQL lists the terms on one column are merged into one argument before the query is sent, since the QL keys its filter by column ([`Input.cpp:29`](../../libs/ql/src/types/Input.cpp#L29)): different operators become the keys of one object, each with a variable of its own, so `created:>=a created:<b` is `{gte:a,lt:b}` and `x:a -x:b` is `{in:[a],nin:[b]}`; the same comparison twice keeps the tighter bound; `-x:a -x:b` is one `nin` of both values; and `x:a x:b` intersects its values, which on a single-value column leaves an empty `in` that matches nothing ([`Syntax.cpp:52`](../../libs/db/src/generators/Syntax.cpp#L52)). Bare words share the one `glob` key as a list, since an operator object holds an operator once ([`Input.cpp:15`](../../libs/ql/src/types/Input.cpp#L15)): `glob` takes a list of patterns, all of which must match, where it took one pattern before Phase 3a ([`Syntax.cpp:64`](../../libs/db/src/generators/Syntax.cpp#L64)), so `pump station` finds *Station pump 3*. A date term is a whole day in the browser's time zone, sent as UTC: the parser builds `new Date(y,m-1,d)`, since `new Date('2026-01-01')` reads as UTC, and sends it by `toISOString()` ([`view.ts:327`](../../web/framework/control/src/lib/model/ql/view.ts#L327)), and the next day is the next calendar midnight, not 24 hours on. With `start(d)` that local midnight, `x:d` is `{gte:start(d),lt:start(d+1)}`, `x:a..b` is `{gte:start(a),lt:start(b+1)}`, `x:>=d` is `{gte:start(d)}`, `x:<d` is `{lt:start(d)}`, `x:>d` is `{gte:start(d+1)}` and `x:<=d` is `{lt:start(d+1)}`; the `@today` forms follow the same rules. A date may carry a time, `created:2026-01-31T14:30`, to the minute or the second (added 2026-11-10, with Phase 3a): it is the minute or the second it names, by the same rules with that span in the day's place. A draft and a saved view keep the typed text, so the day is always the one in the time zone of the browser running the query. `-created:d` and `created:d1,d2` would each need an or, so they are terms the box cannot read. Nor can it read a term on a column of OBJECT kind, such as the status and the two counts the gateway grafts onto a connection's row after the select ([`OpcSessionsQLAwait.cpp:198`](../../apps/OpcGateway/src/ql/OpcSessionsQLAwait.cpp#L198)): the server has no column to filter, which is the test `sortable` makes for `orderBy` ([`graphql-table.ts:78`](../../web/framework/control/src/lib/pages/graphql/table/graphql-table.ts#L78)). On a live-toggle column the header names the live state, and a row is live when the column is null ([`graphql-table.ts:84`](../../web/framework/control/src/lib/pages/graphql/table/graphql-table.ts#L84)), so `has:` and `no:` change places there: on the Resources page `has:enforced` compiles to `deleted:[null]`, and no other term is read on that column. Named by its QL name the column is what it holds, so `has:deleted` is the deleted rows there as on any list (ruled 2026-11-10, on Phase 3a's review). The box parses on every keystroke and queries on Enter, on a suggestion taken and 400 ms after the last keystroke; a term it cannot read, an unknown field, a comparison on text on a GraphQL list, an unbalanced quote, a negated or listed date, a term on a column the server cannot filter, is underlined in the box's error colour, named in the hint under it, and left out of the query, so the view still loads. Suggestions come from a `mat-autocomplete`: with the cursor in a field position the headers, with `no:`, `has:` and `-` before them; after the colon the values, the schema's enum values for an enum column ([`ql-list.ts:294`](../../web/framework/control/src/lib/pages/ql/list/ql-list.ts#L294)), the loaded rows' distinct values for the rest as `colSuggestions` gathers them today ([`ql-list.ts:229`](../../web/framework/control/src/lib/pages/ql/list/ql-list.ts#L229)), `@today` and the comparison signs where the column takes them; a value with a space is quoted as it is inserted. The parsed form is one structure, a list of `{field, operator, values, negated}`, that replaces `fieldFilters` on the view ([`view.ts:430`](../../web/framework/control/src/lib/model/ql/view.ts#L430)) and is serialized as the text itself, so a saved view keeps what the user typed; `View.query` compiles it to the argument list as it compiles `fieldFilters` now ([`view.ts:341`](../../web/framework/control/src/lib/model/ql/view.ts#L341)), and `NodeView` and `WatchView` compile the same structure to a predicate over their rows ([`node-view.ts:54`](../../web/opc/control/src/lib/model/node-view.ts#L54)), with the same grammar and the same null rule, a negated term keeping a null cell. Case differs by host: a GraphQL list compares as its database does, and the node and watch lists compare `field:a` exactly, as they do today. `NodeView`'s and `WatchView`'s schemas declare each column's real type rather than all String ([`node-view.ts:15`](../../web/opc/control/src/lib/model/node-view.ts#L15), [`watch-view.ts:14`](../../web/opc/control/src/lib/model/watch-view.ts#L14)): numbers for the watch list's `sampling`, `revisedSampling`, `queue` and `revisedQueue`; enums for `class`, `dataType` and `status` on the node list and `connection`, `status` and `discard` on the watch list, whose `Filter by…` lists the values the rows hold; `DateTime` for `sourceTime` and `serverTime`; and String for the rest, `id`, `snapshot` and `value` among them, since an OPC value's type varies by row. Both pages draw their own cells, so a declared type changes no rendering. A comparison on these hosts keeps today's rule on any column, numeric when both sides are numbers and text otherwise, and on a time column, whose cell is local text in a fixed-width form, the bounds are `start(d)` formatted by `NodeView.time`. An empty cell matches no comparison there, as a null matches none in SQL, where today's `<` and `<=` take one ([`node-view.ts:63`](../../web/opc/control/src/lib/model/node-view.ts#L63)). A route's built-in filters ([`view.ts:176`](../../web/framework/control/src/lib/model/ql/view.ts#L176)) are written in the same grammar, `filter: "issuer:<null>"` becoming `filter: "no:issuer"`; `<null>` and `<not null>` go. A chip cell clicked, a user's *Google*, adds `field:value` to the filter, as a board's card data does in Projects; a click on another value of the same column joins that term's list, `provider:Google,Key`, the rows with either, and a second click on a value takes it out, the term going with its last (ruled 2026-11-10, on Phase 3b's review). A chip on a column the box cannot filter, a connection's *Error*, is not a click target. The *Deleted* view is a built-in whose filter is `has:deleted`, and the rule that a view without a `deleted` term hides deleted rows ([`view.ts:389`](../../web/framework/control/src/lib/model/ql/view.ts#L389)) stands.

**Fields.** The `Fields` submenu is a checklist of every column the route does not exclude, in the view's order, ticked where displayed; a tick applies at once. The header gains a menu on hover and focus, a `more_vert` at its right end: `Sort ascending`, `Sort descending`, `Group by this field`, `Slice by this field`, `Hide field`, and `Filter by…` for a chip, enum or boolean column the box can filter, which lists its values. Headers drag into order with CDK drag-drop along the header row, the row's cells following, and drop writes the view's field order; `Move left` and `Move right` in the header menu do the same without a drag. A header's right edge is a resize handle, 8px wide with `col-resize`, dragged to set the column's width; the width lands in the field's `Style.flex` as a fixed basis, the form a route already writes ([`view.ts:98`](../../web/framework/control/src/lib/model/ql/view.ts#L98)), so it saves with the view through `toJson` as every style does ([`view.ts:408`](../../web/framework/control/src/lib/model/ql/view.ts#L408)); a double-click on the handle returns the route's width, and `Wider` and `Narrower` in the header menu change it a step at a time without a drag. The name column, or the first displayed column where there is no name, is sticky at the left as Projects pins its title, over the selector's checkbox where there is one; the header row is sticky already ([`graphql-table.html:75`](../../web/framework/control/src/lib/pages/graphql/table/graphql-table.html#L75)). **Sort.** A header click still sorts ascending then descending, never clearing; the header menu's two entries set a direction outright. `Sort by` in the view menu lists the sortable columns with the current ones ticked in order; a click adds a field after the current ones, a click on a ticked field flips it, `No sorting` clears, and a field's position in the list is dragged, or set with `Move up` and `Move down` on a ticked field. The header of every sorted column shows the arrow, and the second and later ones a small index after it. A column `sortable` refuses ([`graphql-table.ts:78`](../../web/framework/control/src/lib/pages/graphql/table/graphql-table.ts#L78)) is absent from both menus. The pager's hidden `id` tiebreak ([`ql-list-resolver.ts:190`](../../web/framework/control/src/lib/services/ql-list-resolver.ts#L190)) stays.

**Group by.** `Group by` names one number, boolean or enum column ([`field.ts:47`](../../web/framework/control/src/lib/model/ql/schema/field.ts#L47)), never one of type `ID`, and `No grouping`. The group field becomes the view's first sort, ascending, kept ahead of whatever the user sorts by, so the rows of a value are contiguous and a page is cut into whole groups at its ends only; a page break inside a group shows the group's header again on the next page. Each group is a header row above its rows, sticky under the column header: the value, as the cell would render it, a chip where the column is a chip, *No <field>* for null, the count of its rows on this page, and the sums `Field sum` chose, the number columns the schema marks as such ([`field.ts:47`](../../web/framework/control/src/lib/model/ql/schema/field.ts#L47)) and never one of type `ID`, each as *Sessions 12*. A chevron on the header collapses the group; the set collapsed is kept in the browser beside the drafts, not in the view. On a browser-side host the groups are cut from the applied rows the same way, counts and sums exact since every row is present. The count of a group over the whole list comes from a `groupBy` query on the group field, the query `Slice by` uses, below, whether or not the view is sliced, and the header reads *12 of 40* when the two differ.

**Slice by.** `Slice by` names one column, the same columns as grouping, and `No slicing`. A panel at the left of the table, 240px, with the field's name and a switcher at its top, *All* with the list's count, then one row per value with its count, the current one highlighted; a click narrows the view to that value and the second click returns to *All*. The chosen value is a slice, not a filter term: it is kept in the browser beside the drafts, the filter box does not change, and the saved view keeps the field alone. The counts honour the filter box, so slicing by provider under `has:email` counts the users with an email. For a GraphQL list they come from one query, `users( groupBy:provider, …filters ){ provider count }`, a `groupBy` argument the QL gains beside `orderBy` and `limit` ([`Input.h:27`](../../include/jde/ql/types/Input.h#L27)): the statement selects the grouped column and `count` ([`SelectAwait.cpp:136`](../../libs/ql/src/ops/SelectAwait.cpp#L136)) and gains a `GROUP BY` beside its `OrderBy` ([`Statement.h:19`](../../include/jde/db/generators/Statement.h#L19)); a grouped foreign key answers the row's `{id name}` as a column does now. A browser-side host counts its rows. The panel collapses to a `Slice` button on a small screen and is absent on a phone.

Projects' board is not taken here (*Open questions* #15): without a card dragged between columns, which is ruled out for now (#4), it shows what `Group by` shows, drawn as columns of cards, and it comes back with drag-to-write. Projects' side panel is not taken: there is no pane beside the table. **Keyboard.** The table is a grid of the WAI-ARIA pattern, one tab stop: `role=grid`, a roving `tabindex` on the focused cell, arrows between cells, Home and End along the row, Ctrl+Home and Ctrl+End to the corners, PageDown and PageUp turning the pager's pages. Enter on a row opens its record's page; Space toggles the row where the list has a selector; Shift+Space selects it where it has none, for the hosts with row actions, and Shift+Up and Shift+Down extend; Escape clears the filter box when it has the focus. The header is the grid's first row: Enter on a header cell opens its menu, and a sort key is Enter on the arrow. `Ctrl+\` focuses the filter box, `Cmd+\` on a Mac, as it does on a Projects view; `/` is the site search's already ([`navbar.ts:176`](../../web/spa/control/src/lib/shared/navbar/navbar.ts#L176)), as on GitHub's own site, and Ctrl+F stays the browser's find (*Open questions* #6). Focus is visible on every stop at WCAG AA, as every control of the site is held to.

## Open questions

1. **The measure.** Projects' shapes, controls and behaviour in the site's Material theme, not its look pixel for pixel. Recommended: the site is one Material surface and a Primer island in it would read as another product; the shapes are what make a view feel like Projects. Ruled 2026-11-08: as recommended - the Material theme stays.
2. **Paging.** The pager stays, and a group, a column and the bar's count are the page's. Recommended: the lists that page are the long ones, the logs above all, and the pager's recent work ([#329](https://github.com/Jde-cpp/opc-hub/issues/329)) is sound; the alternative, loading pages as the table scrolls as Projects does, makes grouping and the board honest over the whole list at the cost of a scroll that never ends on a log. The slice panel's counts are the whole list's either way. Ruled 2026-11-08: as recommended - the pager stays.
3. **Counting by a field.** A `groupBy` argument on a collection query, with `GROUP BY` in the statement, for the slice panel's counts and a group's whole-list count. Recommended: one query per view load, against the alternative of a `count` query per value, which is one per provider or status and grows with the enum. Ruled 2026-11-08: as recommended - the QL gains `groupBy`.
4. **Drag to write.** None now: a card dragged between board columns, or a row into a group, does not write the field. Recommended: which collections take the write is a question per collection, and a drag that fails after the card has landed is the worst of both; a later piece adds it where a route names the field writable. Ruled 2026-11-08: as recommended - no drag-to-write now.
5. **Rows.** No row numbers, no hand order, no inline `+ Add item`, no bulk archive. Recommended: a record has required fields a page asks for, a list's order is its sort, and the hosts with row actions have them in the row. Ruled 2026-11-08: as recommended - none of the four is adopted.
6. **The filter key.** `/` focuses the filter box; Ctrl+F stays the browser's. Recommended: the browser's find is how a user searches the page the pager shows, and `/` is the convention on GitHub's own site; the alternative is Projects' own Ctrl+F. Ruled 2026-11-08: against the recommendation - `/` stays the site search's, which the navbar binds already ([`navbar.ts:176`](../../web/spa/control/src/lib/shared/navbar/navbar.ts#L176)), and `Ctrl+\` focuses the filter box, `Cmd+\` on a Mac, the key that does so on a Projects view; Ctrl+F stays the browser's find.
7. **A bare word.** It searches the name column alone for the GraphQL lists; every text cell for the browser-side hosts. Recommended: an or across columns is not in the QL today, and the name is what a user types to find a row; the alternative adds a `search` argument to the QL that ors the text columns, for a later piece if asked for. Ruled 2026-11-08: as recommended - the name column alone. Ruled 2026-11-09, on review: it compiles to `glob`, the one pattern operator all three databases take, since sqlite and SQL Server refuse `regex`; on the GraphQL lists the match is case-sensitive on sqlite and follows the column collation on MySQL and SQL Server. Ruled 2026-11-09, on the plan's review: several bare words must all match, each a pattern in a list under `glob`, which the QL gains; the alternative read them as one phrase and needed no QL change.
8. **The pane's url.** The record's route under the list's, so the url is the record's as today, and the screen decides whether the list shows beside it. Recommended: one url per record, bookmarkable and the same on a phone; the alternative, `?open=<slug>` on the list's url, keeps the routes as they are and gives a record two urls. Ruled 2026-11-08: against the recommendation - no pane beside the table, and none in this spec: a row opens the record's page as it does today, with no route or url changes. A pane across the bottom of the list can come later, under [#256](https://github.com/Jde-cpp/opc-hub/issues/256).
9. **Built-in views.** Kept, undeletable, unrenamable, duplicable, `Save` on one saving a new user view under a name. Recommended: a route's views are the page's defaults and *Deleted* is the one way to a deleted record; Projects has no equivalent to lose. Ruled 2026-11-08: against the recommendation - the built-in views are a starting set, shown only while the user has saved none; the first save keeps the whole set as the user's own, and from then every view is theirs to delete, rename, duplicate and save over. Deleting them all, one by one, shows the route's again, with no reset entry, and `has:deleted` in any view still reaches the deleted records.
10. **Shared views.** Later, as the clients spec ruled for the watch list. Recommended: a `profiles` row per user is the store, and a shared view wants a table, rights and an owner, which is a spec of its own. Ruled 2026-11-09: as recommended - shared views later.
11. **Roadmap.** Not offered. Recommended: no list today has the start and end a roadmap lays out; the calendar's exceptions and OEE's downtime are the first that will, and OEE draws its Gantt already ([`../oee/spec.md`](../oee/spec.md)). Ruled 2026-11-09: as recommended - no roadmap layout here; it is taken up when the first list with a start and an end is built.
12. **The profile column.** `profiles.value` widened to a text type. Recommended: the blobs are JSON and 4096 characters is already close for a list with several views; the alternative, a row per view under `qlList/<collection>/views/<name>` with an order row, keeps the column and multiplies the writes. Ruled 2026-11-09: against the recommendation - a row per view, keyed by the view's number since names may repeat (#14), `qlList/<collection>/views/<n>`, with the tab order in an index row; the column stays as it is.
13. **Field names in the filter.** The header's name, case-insensitive and quoted when it has a space, with the QL name accepted too. Recommended: a user types what they read in the header, and the suggestions write it; the alternative, the QL name alone, makes a user type a name the screen does not show.
