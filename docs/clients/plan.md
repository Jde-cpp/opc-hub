# Clients implementation plan - 2026-10-20

A plan for [`spec.md`](spec.md) (2026-10-20), whose fourteen open questions were ruled and whose review ([`clients-spec-review.md`](../../../reviews/clients-spec-review.md), 21 findings) was folded the same day; this plan's own review ([`clients-plan-review.md`](../../../reviews/clients-plan-review.md), 23 findings) was ruled and folded 2026-10-21, twelve of its findings into the spec as well. It has the shape of the servers plan ([`../servers/plan.md`](../servers/plan.md)) and the OEE plan ([`../oee/plan.md`](../oee/plan.md)): prerequisites that are each useful alone, then the spec's pieces in dependency order, each phase a PR or two with its own tests, and three milestones that merge end to end. Status is tracked on GitHub: [#411] is the parent, each phase below names its issue, whose body is the plan's text at filing and is refreshed from here after a fold, as the servers plan's are, [#353] and [#318] being Phases 0.1 and 10 with the plan's text appended to theirs, and the milestones are [I](https://github.com/Jde-cpp/opc-hub/milestone/14), [II](https://github.com/Jde-cpp/opc-hub/milestone/15) and [III](https://github.com/Jde-cpp/opc-hub/milestone/16).

Line numbers cite opc-hub2 at `fc413ed1`, as the spec does; open62541 refs are v1.5.9.

Six things the spec's piece table does not say:

- **The connect's blocking pool comes first.** `ConnectAwait` builds its client and connects on the executor thread that awaits it ([`ConnectAwait.cpp:129`](../../apps/OpcGateway/src/async/ConnectAwait.cpp#L129)), and `testConnection` does the same, which is [#353], open and unscheduled. `discover` is a third such caller, a throwaway client against a url of the caller's choosing, and the spec's piece 1 says "after #353, or bringing its blocking pool": this plan takes #353 as Phase 0.1, so the pool is built once, with the two callers it names moved onto it, and discovery joins them in Phase 2.
- **The two L pieces are two phases each.** Piece 6 is the gateway's half, the socket's parameters, the filter, the merge and the modify, which the suite proves through the socket with no page, and the web's half, the page; piece 7's trend follows the page. Piece 8 is the registry with the decode on the QL side, which every `node` and `history` read gets at once, and then the socket's `structure` member with the historian's pushes and the web's rendering.
- **The OpcServer's share rides in the gateway phase that needs it.** The Execute mapping and the test method with Phase 10, the test event source with 11, the test condition with 12a, each where its suite first fails without it, as the OEE plan's pumps members ride with its host. 12a's condition object is the shared server library's ([`../servers/plan.md`](../servers/plan.md), 1a) and is built there if [#380] has merged, else in the OpcServer, in the `Jde::Opc::Server` namespace both keep, so the move is 1a's directory move and nothing else.
- **Three phases change the socket's protos**, 6a, 8b and 11, each adding a message or a member. The web's bindings are generated from the gateway's own files, symlinked under `web/opc/proto` and built by ts-proto into `jde-proto` ([`web/CLAUDE.md:19`](../../web/CLAUDE.md#L19)), so each phase regenerates and the two sides cannot drift; nothing keeps compatibility with an earlier dev build's messages.
- **The pages are loaders.** The watch list is a route under the gateway's app page, `apps/gateways/<instance>/watch` beside `templates/:slug` and `groups/:slug` ([`app.routes.ts:106`](../../web/opc/site/app/app.routes.ts#L106)), through a loader in [`opc-pages.ts:1`](../../web/opc/control/src/lib/pages/opc-pages.ts#L1), the rule [#351] set for the initial bundle. The Types and Views pages are no new route: the browse tree's catch-all takes every segment under a connection ([`app.routes.ts:32`](../../web/opc/site/app/app.routes.ts#L32)), so `Types/…` is a path the resolver hands the gateway with `root: Root`.
- **The new settings keys go in hidden, with their defaults**, by CLAUDE.md's rule: `/gateway/rejectedCertDir` in Phase 3 and `/gateway/subscription` in 6a, in [`Opc.Gateway.jsonnet`](../../apps/OpcGateway/config/Opc.Gateway.jsonnet) as `hist.delay` is ([`:59`](../../apps/OpcGateway/config/Opc.Gateway.jsonnet#L59)); the per-connection columns of Phase 1 are nullable and null means the gateway-wide value, so no key is added for them.

## Risks

- **The registry's arrays under live clients.** open62541 reads `customDataTypes` on every decode and frees a client's `cleanup` arrays with its config ([`ua_client.c:261`](https://github.com/open62541/open62541/blob/v1.5.9/src/client/ua_client.c#L261)), so the registry owns its arrays, an append-only chain each client chains `cleanup:false` nodes to, and frees nothing while the row lives; a type redefined on the server is not refreshed until the row is purged, the spec's *Later*, and a value decoded against the chain is serialized at once and never kept. A value received before the registry held its type is the opaque form the serializers already know, not an error.
- **The merge's lock order.** `ItemParameters` runs under the monitoring lock and may not call the client ([`MonitoringNodes.h:32`](../../apps/OpcGateway/src/types/MonitoringNodes.h#L32)); the merge is computed there and the modify posted after release, so two changes racing each post a modify from the map as it stood, and the last to run matches the map. A modify the server refuses leaves the item as it was and logs, as the group host's does today.
- **The condition object without open62541's A&C.** 12a writes a state machine by hand, and the Part 9 surface is large; the scope is what 12b shows and tests, the four states, one branch, Retain, the three methods and the refresh, with shelving and the rest the spec's *Later*.
- **One subscription per client.** A refresh replays to every listener on the client's subscription, which the spec accepts; 12a's `createEventEx` keeps it from every other subscription. A publishing interval per view, which would need a subscription per view, is the spec's *Later*.
- **The type fetch on a large server.** One synchronous service per connect and reconnect, on the strand as the namespace drain is, bounded by open62541's own depth and count limits; a server that refuses the Types browse leaves the registry empty and its structures opaque, which the cell says.
- **The pool's size.** A Discover against an unroutable host holds a pool thread for the probe's timeout, as a connect does; #353's test keeps the executor clear, and a bound on the pool is its decision.
- **The proto changes.** Three phases regenerate the web's bindings; the hub serves one web build with one gateway, so nothing reads an older message, and the hub's socket session runs the gateway's unchanged ([`WebServer.cpp:4`](../../apps/OpcHub/src/WebServer.cpp#L4)), its [`SocketTests.cpp`](../../apps/OpcHub/tests/SocketTests.cpp) proving one of each.
- **Windows.** Nothing new to build or link; the rejected directory sits under the data folder as `ssl/servers` does, and 0.1's pool is [#353]'s to choose, nothing in it platform-specific.
- **Spec drift.** A PR that changes behaviour changes [`spec.md`](spec.md) with it, and the open questions' rulings are folded as they come; 12a's condition object is the likeliest to need one.
