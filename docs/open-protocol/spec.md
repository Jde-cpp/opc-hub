## Overview

The gateway is a UA client and nothing else: a connection is a url and a certificate URI ([`ServerCnnctn.h:21`](../../apps/OpcGateway/src/types/ServerCnnctn.h#L21)), and a device reaches the product only through an OPC UA server. A tightening controller has none to count on. The PF6000 and PF8 manuals name no OPC UA anywhere ([PF6000][pf6k34], [PF8][pf8]); the OPC Foundation's companion specification for tightening, *OPC UA for Joining Systems* ([OPC 40450-1][ijt], 1.01.0, 2025-10-06), has no Atlas Copco controller that claims it in any source found. What every tightening controller on a line does speak is Open Protocol: Atlas Copco's, framed ASCII over TCP on 4545 ([§2.1.1][op]), implemented by Desoutter, Stanley, Ingersoll Rand, Cleco, Bosch Rexroth and Kolver controllers besides ([Tulip][tulip], [DeMeter][demeter]), and the interface a line PLC or an MES takes results through.

What a tightening controller gives is not what a PLC gives. A PLC is tags, read when asked. A tightening controller is results, one per rundown, pushed when it happens: a record of the final torque and angle against their limits, OK or NOK, the parameter set that ran, the batch, the VIN, the controller's time and a tightening id ([§5.8.2][op]). And it takes commands, not writes: select a parameter set or a job, disable or enable the tool, download a VIN. So the driver here pushes values and answers methods, where the Allen-Bradley driver was a read-through cache with writes; the server it sits behind, and everything the gateway does with that server, is the same.

There is no library. No C or C++ implementation is both maintained and licensed for linking; the mature ones are OpenProtocolInterpreter, a C# parser under MIT ([github][opi]), and node-open-protocol, a JavaScript client under GPL 3 ([github][nop]). The protocol is small, so the codec is the product's, on asio, and the same codec plays the controller in the suite and in the emulator, where the PLCs spec took the library's simulator because the library was the protocol.

Line numbers cite opc-hub2 at `af6ea641`, main with the web and OpcServer refactors merged, re-pinned at the plan review's fold. Refs re-anchored on 2026-10-23, the UA server library's move among them, cite branch `servers-1a-ua-server-library`. open62541 refs are v1.5.9, the version the build links. Section numbers are the Open Protocol specification's, Atlas Copco 9836 4415 01, Release 2.20.1; Atlas Copco publishes no download of it, and the copy cited is the one OpenProtocolInterpreter's repository carries ([PDF][op]). The per-product appendices are Atlas Copco's own, the PF6000's on ServAid ([PF6000 appendix][pf6kapp]).

**Roles.** The driver turns a tightening controller into a UA server the gateway already knows how to use, and its server is not a product endpoint: it binds loopback and only the gateway's own clients reach it. A SCADA or MES that wants the results takes them from the servers spec's endpoint, with the group's history behind them, or keeps its own Open Protocol connection where the controller has a slot for it (*Connections*). Nothing is added to the deploy: there is no library, so nothing joins the superbuild, the third-party notices or the installers' file lists ([`files.txt:22`](../../apps/OpcHub/setup/files.txt#L22); [`build-deb.sh:160`](../../apps/OpcHub/setup/linux/build-deb.sh#L160)), no port opens, and the driver's connection is outbound, to the controller's 4545 or its virtual station's port.

**The protocol.** A message is a 20-byte ASCII header, the length, the MID, the revision, a no-ack flag, the station and spindle, a sequence number and two part fields, then a data field of two-digit parameter ids and fixed-width values, and a NUL the length does not count. The receiver finds the end by the length, since MID 0900 carries binary after its NUL. A message is at most 9999 bytes, or 99 linked parts ([§2.2, §2.3, §3.8][op]). The integrator opens TCP to the controller and sends MID 0001; the controller answers MID 0002, or MID 0004 with an error code, and answers nothing else first ([§3.1, §5.2.1][op]). After that, each direction has one message outstanding at a time ([§3.2.1][op]).

The integrator chooses one of two ways to acknowledge. At application level, a subscription's push is answered by its own ack MID, 0062 for a result. At link level, OP 2.0's MID 9997 and 9998 answer against a sequence number running 1 to 99 per direction; this replaces the per-topic acks, and the specification calls it "almost a mandatory" ([§3.2–3.2.2][op]). The driver takes link level where MID 0002 revision 6 says the controller numbers its messages, and application level otherwise (*Open questions* #7). A repeat of the number last acknowledged is a retransmission, answered with the same 9997 and dropped; any other number out of order is answered by 9998 carrying the expected one, then a disconnect and a reconnect, as the specification prescribes ([§3.2.2][op]). MID 0001 and 0002 go unnumbered and the numbers start at 1 after them ([§2.2.5][op]); the keep-alive is numbered as any request is; and a message the controller sends unnumbered on a numbered link, which the specification allows it ([§3.2][op]), is acknowledged by its topic's MID.

The controller drops a connection that is silent for 15 s, a time a PF6000 or PF8 sets per virtual station between 15 and 60 s ([PF6000 manual][pf6k]). The driver sends MID 9999 after `keepAlive`, 10 s, without a message either way, which is the specification's own suggestion ([§5.28.1][op]). A request or an ack unanswered within `replyTimeout`, 10 s, the specification's suggestion over TCP in place of resends ([§3.3.5][op]), is a lost link.

There is no revision negotiation: a request in a revision the controller lacks is answered by MID 0004 with code 74, 76 or 97 ([§5.2.1, Table 23][op]), or in the revision the controller has, as §1.4's example answers a MID 0052 at 2 in revision 1 ([§1.4][op]). So the driver asks for the highest revision it decodes and steps down on those codes, MID 0001 from 6 and MID 0061 from 7, as the open clients do ([node-open-protocol][nop-session]), and it decodes every reply and push by the revision in its own header, so a controller that answers lower is read right. It stays under the row's `revisions` ceilings, keeps the revision the controller answered for the connection's life, whichever side stepped down, and shows it in `_Op.Revisions` (*Open questions* #8). A ceiling named for the MID a request asks for bounds the request, so `{"0061": 3}` caps the MID 0060 that subscribes to it.

The MIDs the driver speaks:
- 0001 to 0005;
- 0014 to 0017 for the selected parameter set, and 0018;
- 0034 to 0038 for job info and job select;
- 0042 and 0043;
- 0050 to 0054 for the VIN;
- 0060 to 0065 for results and their recovery;
- 0070 to 0077 for alarms;
- 0080 and 0081 for the controller's time;
- 9997 to 9999.

It subscribes by the per-topic MIDs, not the generic 0008, since the PF6000 appendix lists no 0008 ([PF6000 appendix][pf6kapp], Table 1).

**The codec.** `Jde.Opc.OpenProtocol`, in `libs/opc/openProtocol`, has no open62541 and no I/O in its core: a header and field codec, a type per MID the driver speaks, each revision's fields, tested from byte buffers. A session runs on an asio TCP socket on the gateway's executor ([`execution.h:10`](../../include/jde/fwk/process/execution.h#L10)), one strand per row, with the read loop, the outstanding request, the acks, the keep-alive timer and the reconnect on that strand. The controller's side of the same codec, the accept, MID 0002 and the pushes, is in the library too, for the suite and the emulator. A frame the codec refuses is logged and dropped, with no disconnect of its own: one whose header reads is acknowledged first, and bytes whose length does not read are dropped through the next NUL, where a frame can start again. A controller on a plant network is untrusted input: the decoder bounds the length, reads each part field as one character by the specification's §7.1 table, refuses a field that is not its width or a digit field with mixed content, and has a fuzz target. A digit field that is all spaces is its default, the table's where it names one, revision 1, station 1, spindle 1, and not used otherwise, and a revision of `000` is 1 ([§2.2.2, Table 1][op]; plan review #10); the specification's own MID 0001 example carries nine of them ([§5.2.1][op]). In the data field, a field of spaces is a value not sent ([§2.3, Table 3][op]), and a number may have spaces after its digits, as the specification's own MID 0061 example writes its tightening id ([§5.8.2][op]). A text byte past Table 3's 0x7F is read as its Latin-1 character, held as UTF-8 and written back as that byte, so a name outside ASCII keeps its result whatever code page the controller writes. A time whose digits name no date, `0000-00-00:00:00:00` among them, is not set, as a field of spaces is. Bytes after a revision's last field, as a later firmware's parameters would be, are ignored and logged under the library's tag. An acknowledgement is read by its data, whatever revision its header carries: no request names the revision of a MID 0004 or a MID 0005, a frame refused there would leave its request to `replyTimeout` and the link to its loss, and Jarrekstar's simulator writes the revision of the request it answers into both. So MID 0005 is read as Table 24's one layout, and MID 0004 under a revision past 1 with a code of two digits where its frame holds no third ([Tables 21, 22 and 24][op]; the plan's *Phase 10*, 10a's *Built*). The driver sends digits. Its log is the library's own `openProtocol` tag, registered as the OPC library's are ([`logTags.h`](../../include/jde/opc/openProtocol/logTags.h)), with each frame in and out at Trace when `/gateway/drivers/openProtocol.log` is on.

**Connections.** A controller takes a bounded number of Open Protocol clients: several per virtual station on a PF6000 or PF8, with no number stated; two over TCP on an MT Focus 6000 ([MT Focus 6000][mtf], p. 4); an unstated number on a PF4000. The session types Actor, Viewer and Classic decide who may command, a Viewer's command answered by code 92 and a second Actor refused with 35 ([§3.3.4][op]). The gateway's connection is one more beside the line PLC's or an MES's. Where the controller has one slot, the gateway takes it from them, which a site decides before it adds the row.

A PF6000 or PF8 can lock the tool when an Open Protocol client disconnects, set per virtual station as its *Disconnect action* ([PF6000 manual][pf6k]). A row's virtual station keeps that action at None, or the line stops whenever the gateway restarts, and the help says so. For the same reason, the driver never asks for MID 0001 revision 8's tool lock at disconnection ([Table 12][op]).

**The row.** `server_connections` ([`opcGateway-meta.jsonnet:22`](../../apps/OpcGateway/config/opcGateway-meta.jsonnet#L22)) grows `kind`, `ua` by default, and `driver`, a json text. Both are nullable, and null means a UA row. `kind` is `open-protocol` here, `ab-eip` when the PLCs spec un-parks, and `flow` for the flows spec's flow server, a row with no driver behind it (plan review #7), with that spec's `plc`, `path` and `tag_list` as members of `driver` rather than columns of their own (*Open questions* #2).

For an Open Protocol row:
- `url` is `open-protocol://<host>[:<port>]`, 4545 by default ([§2.1.1][op]), or a virtual station's own port where the controller has several ([PF6000 manual][pf6k]).
- `driver` holds `timeZone`, the IANA zone the controller's clock keeps, the gateway's own by default (*Results*), and `revisions`, per-MID ceilings for a controller that answers a revision it implements badly, `{"0061": 3}`.
- `certificate_uri` is the driver server's applicationUri, which is the gateway's own. The save refuses a value and `ServerCnnctn` supplies it for a driver kind, the column staying null (plan review #6). It is the server URI a client holds the endpoints against ([`UAClient.cpp:478`](../../apps/OpcGateway/src/UAClient.cpp#L478)); its being set selects Sign & Encrypt; and the pair the driver server presents carries that URI in its SAN.
- `default_browse_ns` is the driver server's one namespace, 2, supplied the same way.

The insert procs take the new columns ([`sqlite/gateway_server_connection_insert.cpp:7`](../../apps/OpcGateway/config/sql/sqlite/gateway_server_connection_insert.cpp#L7), [`gateway_server_connection_insert.sql:4`](../../apps/OpcGateway/config/sql/mysql/gateway_server_connection_insert.sql#L4)). The save rules run on insert, and on update over the merged row: a known `kind`, a url of its scheme, and a `driver` the kind's rules accept. A UA row takes no `driver` and no `open-protocol://` url; an Open Protocol row's is an object of `timeZone` and `revisions` alone, a ceiling a revision from 1 to 999. A kind with a driver refuses a value for `certificateUri`, `defaultBrowseNs`, `securityMode` or `securityPolicy`, and an update that changes a row's kind to one writes null to the four.

`connectionEdited` ([`ServerCnnctnMAwait.cpp:122`](../../apps/OpcGateway/src/ql/ServerCnnctnMAwait.cpp#L122)) treats a change to `kind` or `driver` as it treats one to the url: the row's clients go first ([`UAClient.cpp:310`](../../apps/OpcGateway/src/UAClient.cpp#L310)), then the driver server stops and the driver starts again, and the clients reconnect to it on the new row. A row inserted while the gateway runs gets its server then, a delete stops it as a purge does, and a restore starts it (plan review #3).

The client dials the driver server, not the url. Where the connect sets the url it dials ([`UAClient.cpp:1017`](../../apps/OpcGateway/src/UAClient.cpp#L1017)), a row of a kind with a driver takes `opc.tcp://127.0.0.1:<port>`, and any other kind, `flow` among them, dials its stored url. `ReachableUrl` beside it, the fallback probe for a name with several addresses ([`:988`](../../apps/OpcGateway/src/UAClient.cpp#L988)), is left alone. A driver row's `testConnection` never reaches `TestConnectAwait` ([`TestConnectAwait.h:11`](../../apps/OpcGateway/src/async/TestConnectAwait.h#L11)), since it builds no client.

The clients spec's columns ([`../clients/spec.md`](../clients/spec.md) *Connection settings*, [#413](https://github.com/Jde-cpp/opc-hub/issues/413)) keep their meaning where they have one, the session and request timeouts, the keep-alive and the TTL; the mode and the policy are fixed, and the save refuses a value for either.

`testConnection( opc, url, certificateUri )` ([`TestConnectionQLAwait.cpp:40`](../../apps/OpcGateway/src/ql/TestConnectionQLAwait.cpp#L40)) takes `kind` and `driver` as optional arguments, under the same right, Update on `serverConnections` ([`:44`](../../apps/OpcGateway/src/ql/TestConnectionQLAwait.cpp#L44)). For an Open Protocol row it opens the TCP connection, sends MID 0001 with the step-down, sends MID 0003 and closes. In place of the server description and the namespaces, it reports what MID 0002 answered ([Tables 13–20][op]): the controller name, the system type and subtype, the supplier code, the Open Protocol, controller and tool software versions, the serial number, and the station's id and name, as `controllerName`, `systemType`, `systemSubtype`, `supplierCode`, `openProtocolVersion`, `controllerSoftwareVersion`, `toolSoftwareVersion`, `controllerSerialNumber`, `stationId` and `stationName`, each null where the revision MID 0002 answered at carries none. A controller that does not start communication is the mutation's error, with the socket's reason or MID 0004's.

**The driver server.** There is one per driver row, whatever its kind, under `apps/OpcGateway/src/drivers/`: a `DriverHost` that owns the server, and an `IDriver` per kind that builds the address space, feeds the values and answers the methods. The Open Protocol driver is under `drivers/openProtocol/`. This is the PLCs spec's `PlcHost` (its *The driver server*) made kind-agnostic, and its rules carry over as written there.

It sits on `Jde.Opc.UAServer`, the library the servers spec moves out of the OpcServer ([`../servers/spec.md`](../servers/spec.md) *The server library*; the servers plan's phase 1, [#380](https://github.com/Jde-cpp/opc-hub/issues/380) and [#381](https://github.com/Jde-cpp/opc-hub/issues/381)). Its `UASettings` are filled from the row and the `/gateway/drivers` block:
- the process's own `/http/ssl` pair as the endpoint's certificate, as the gateway's endpoint presents it;
- bound to `127.0.0.1` on `portBase + server_connection_id`, 4870 plus the row's id, which is stable for the row's life and never typed, a collision logged at Error naming the port and `portBase`;
- Sign & Encrypt under Basic256Sha256, and no None endpoint;
- a trust list of two, in memory, fed to the channel's PKI and to the session's alike, as the OpcServer's one list is ([`UATrust.h:24`](../../include/jde/opc/server/UATrust.h#L24)).

The two certificates on that list:
- The certificate the gateway issued for the slug ([`UAClient.h:135`](../../apps/OpcGateway/src/UAClient.h#L135)), which a web session's channel presents.
- The process's own `/http/ssl` pair, which the collector presents for its channel and its token alike. A certificate credential takes the app client's pair for both ([`UAClient.cpp:359`](../../apps/OpcGateway/src/UAClient.cpp#L359)), and the collector is one unless `hist.credentials` names a user ([`HistHost.cpp:103`](../../apps/OpcGateway/src/hist/HistHost.cpp#L103)).

For that list, the library's `UASettings` gains an in-memory trusted list beside its directories, holding the two files' paths and re-reading them on a failed verify, as the OpcServer's list heals a re-issue. The host makes sure the slug's certificate exists before it builds the list, since the gateway issues it on a web user's first connect and re-issues it when it expires ([`UAClient.cpp:307`](../../apps/OpcGateway/src/UAClient.cpp#L307); plan review #4). Anonymous is off; the token types are certificate and issued; there are no users and no rejected directory. The library's `limits` are open62541's own, except `maxAsyncOperationQueueSize`, which the block's `maxAsyncOperations` sets, and the `queueSizeLimits` maximum, which a kind may raise (*Backfill*). Its applicationUri is the gateway's own, the SAN of the pair it presents, which the suite's gateway `http` block already carries ([`Opc.Tests.jsonnet:52`](../../apps/OpcGateway/tests/config/Opc.Tests.jsonnet#L52)). Its applicationName is `Jde-Cpp <kind> <slug>` with no bracketed suffix, since a driver row keeps no instance schema for the node-access page to address (*Sessions and rights*).

Its sessions are `UAAccess`'s. A web user's client sends an issued token carrying the hub session ([`OpcServerSession.h:12`](../../apps/OpcGateway/src/auth/OpcServerSession.h#L12)). The hub resolves it in-process through the lookup the servers spec's endpoint adds ([#382](https://github.com/Jde-cpp/opc-hub/issues/382)); a split gateway resolves it over the socket.

The collector presents the process's certificate, which `UASettings` maps by an own-certificate rule to the gateway's own user, with no hub lookup. When this was written the hub held no user for its own key: a user is keyed to a public key by a socket login ([`LoginAwait.cpp:52`](../../libs/access/src/server/awaits/LoginAwait.cpp#L52)), and the hub's app client makes none ([`HubAppClient.h:9`](../../apps/OpcHub/src/HubAppClient.h#L9)). Since the release the hub enrolls its certificate as a user of its own, for the collector's sessions on the bundled OpcServer ([`hubStartup.cpp:52`](../../apps/OpcHub/src/hubStartup.cpp#L52)), so a lookup would answer in both shapes. It is skipped in both all the same ([`UAAccess.cpp:237`](../../libs/opc/server/src/UAAccess.cpp#L237)): a loopback server a process runs for itself admits that process as itself, with nothing asked under the service lock, as the user the host names for its pair ([`GatewayAppClient.h:11`](../../apps/OpcGateway/src/GatewayAppClient.h#L11)). That is the user a lookup would find: the hub names its certificate's enrolled user ([`hubStartup.cpp:54`](../../apps/OpcHub/src/hubStartup.cpp#L54)), the one the bundled OpcServer's lookup finds, and a standalone gateway its own login's. So the collector is one user on every server it reads.

The gateway's own clients verify a server's certificate against `/gateway/trustedCertDirs` ([`ServerTrust.cpp:29`](../../libs/opc/shared/src/ServerTrust.cpp#L29); [`Opc.Gateway.jsonnet:53`](../../apps/OpcGateway/config/Opc.Gateway.jsonnet#L53)), and the process's own pair is in neither shipped directory. So a driver row's client anchors that pair in memory beside the directories, an extra anchor the verifier's context takes for any driver kind. The shipped list and `verifyServerCertificate` keep their meaning.

The server starts with the gateway, after the access snapshot ([`gatewayStartup.cpp:66`](../../apps/OpcGateway/src/gatewayStartup.cpp#L66)) and before `HistHost::Start` ([`:70`](../../apps/OpcGateway/src/gatewayStartup.cpp#L70)), which kicks each group's first subscribe, so that subscribe finds it listening. It runs on a thread of its own, one per row, as the OpcServer's does. It stops with its row, through a shutdown hook registered after the UA clients' ([`:68`](../../apps/OpcGateway/src/gatewayStartup.cpp#L68)), since the hooks run in registration order ([`lifecycle.cpp:120`](../../libs/fwk/src/process/lifecycle.cpp#L120)): the collectors unsubscribe, the clients close their sessions on a live server, then the servers stop. The clients' hook posts each close and returns, so a server's stop, the shutdown's and a row's alike, waits up to two seconds for the sessions that were open when it began. A server that cannot start, at the gateway's start or for a row made or changed while it runs, is logged and the row stands, so one row's held port takes neither the gateway nor another row's server down. The endpoint's hook goes ahead of the historian's because the endpoint reads it; a driver server is what it reads. Until the servers plan's phase 1 lands, the driver waits for the library rather than link `Jde.Opc.ServerLib` as it is, which the servers spec's #11 declined for the gateway for its libxml2 and app-client baggage.

**Address space.** It is fixed, the same for every Open Protocol row, built when the server starts and before the controller first answers. Every variable is a stored value the driver writes, and no read reaches the controller. The strand posts each write to the server's own thread ([`UAServer.h:42`](../../include/jde/opc/server/UAServer.h#L42)) and makes no `UA_Server_*` call itself. A write waits for the service lock, and `ActivateSession` holds that lock on the server's thread through an issued token's lookup ([`UAAccess.cpp:244`](../../libs/opc/server/src/UAAccess.cpp#L244)), which in a split gateway needs an executor thread to answer; a write waiting on the strand's executor thread could hold up the very lookup it waits for. Under Objects, in the row's one namespace, URI `urn:jde:<slug>:open-protocol`, with each NodeId the string of its path, `s=Result.Torque`:

- **`Result`.** An object with a variable per field of MID 0061, revisions 1 to 7 ([§5.8.2][op]), named in the specification's words, camel-cased. The exceptions are the cell id, the channel id and the controller name, which `_Op.Identity` carries. The types:
  - `TighteningId` is a UInt32, its ten digits topping out at 4294967295.
  - `Time` and `PsetChangeTime` are DateTime (*Results*).
  - `Status`, the tightening status, is a Boolean, true for OK.
  - The statuses with listed codes, `TorqueStatus`, `AngleStatus`, `BatchStatus`, `RundownAngleStatus` and the rest, are a Byte holding the specification's code: 0 low, 1 OK, 2 high, and for the batch 0 NOK, 1 OK, 2 not used, 3 running.
  - `Torque`, `TorqueMin`, `TorqueMax` and `TorqueFinalTarget`, and the self-tap and prevail torques, are a Double, the wire's integer over 100 ([Table 108][op]), in the unit revision 3's `TorqueUnit` names, Nm when nothing does ([§2.3.1][op]).
  - `Angle`, `AngleMin`, `AngleMax`, `AngleFinalTarget` and the rundown angles are a Double in degrees, with revision 7's final angle decimal replacing `Angle`'s whole degrees where it is sent.
  - `TighteningErrorStatus` and `TighteningErrorStatus2` are a UInt32 of their bits.
  - `Pset`, `JobId`, `BatchSize`, `BatchCounter`, `JobSequenceNumber`, the sync tightening id and the current-monitoring values are UInt16; `Strategy`, `TorqueUnit` and `ResultType` are a Byte; `StrategyOptions` is a UInt32 of its bits.
  - `Vin`, `PsetName`, `ToolSerialNumber`, the identifier parts 2 to 4 and the customer error code are a String.

  A field the settled revision does not carry reads `Bad_NotSupported`, set once when the subscription is accepted, a millisecond past the last result's source timestamp, so a group member over it stores that one status after the results; a result whose own header names a lower revision sets it for the fields that one lacks, at that result's time, and so does a found result, a MID 0065, for what it does not carry (*Backfill*). A field a result carries with no value, its bytes all spaces, reads `Bad_NotSupported` at that result's time too. Each Bad status stands over the type's zero, since the server refuses a typed variable a value of none.
- **`Counters`.** `Total`, `Ok` and `Nok`, each a UInt64 (*OEE*).
- **`Selected`.** `Pset` from MID 0015 and `Job` from MID 0035, each a UInt16, and `Vin` from MID 0052, a String, with revision 2's identifier parts beside it, `IdentifierPart2` to `IdentifierPart4`.
- **`Alarm`.** `Code`, a String, the four-character error code of MID 0071, five from revision 2; `Active`, a Boolean; and `Time`, a DateTime, the alarm's own time in the row's zone, from MID 0071 and MID 0076. MID 0071 is an alarm raised, `Active` true; MID 0076, the status sent as the subscription is accepted, is written as it stands, but that one of no alarm and no time leaves `Time` as it is; and MID 0074, the alarm acknowledged on the controller, is `Active` false under the code it carries, `Time` as the alarm left it, where that code is the alarm `Alarm` holds: one of another code, an older alarm's, leaves `Alarm` as it is.
- **`Commands`.** An object holding the methods (*Commands*), each at `s=Commands.<method>` with its one argument in an `InputArguments` property under it.
- **`_Op`.** The diagnostics, readable by any session:
  - `Connected`, true while the session with the controller is up;
  - `Since`, a DateTime, the last change of `Connected`, the driver's start until the first;
  - `Url`;
  - `LastError`, the last MID 0004's MID, code and name, or the socket's error, of each failed attempt too, kept once the link is back;
  - `Reconnects`, a UInt32 of the links that came back after a loss since the driver started, as the endpoint's `_Connection` counts them;
  - `Identity`, a String, the text of a json object of MID 0002's fields under the names `testConnection` reports them by, a field its revision lacks left out;
  - `Revisions`, a String of the revision settled per MID, a subscription under the MID it pushes, `0001:6 0061:7 0071:3`;
  - `LinkLevel`, a Boolean;
  - `Results`, every result written to `Result`, and `LostResults`, the recoveries that ended short of the last result written (*Backfill*), UInt64 since the driver started;
  - `Skew`, a Double of the controller's clock less the gateway's in seconds, `Bad_WaitingForInitialData` until the first clock read and `Bad_NotSupported` where the controller answers no MID 0080.

  `Identity`, `Revisions` and `LinkLevel` keep the last connection's through a loss.

Every variable has AccessLevel CurrentRead, WriteMask 0 and MinimumSamplingInterval 0. Until the first result, every `Result` field reads `Bad_WaitingForInitialData` and `Counters` read Good 0; the first result replaces the one and advances the other. `Selected`, `Alarm` and `_Op.Connected` follow the link. The four subscriptions of `Selected` and `Alarm` are asked at each connect behind the results' and the clock's read, and a report is written as one post, sourced at its receipt, as the loss of the link is, so a variable's source timestamps increase whatever the controller's clock. Each variable reads `Bad_WaitingForInitialData` until its first report, and `Bad_NotSupported` where a report has no value for it or the controller refuses its subscription, the refusal in `_Op.LastError`, until a later connection's subscription is accepted, when the refused one's variables wait for their report again. Losing the link sets `Bad_NoCommunication` on each that read Good, keeping its last value, and each one's next report replaces it; the link's return writes nothing. `Result` and `Counters` keep their last value and status across a loss. A result is a thing that happened, not a reading that went stale, and a Bad record between two results would land a backfilled result before it (*Backfill*). Whether a controller pushes the current parameter set, job or VIN when the subscription opens, or only on the next change, and whether it sends the alarm's status where no alarm is active, is a hardware check (*Open questions* #15); until a report comes, the value stays Bad.

**Results.** MID 0061 arrives on the strand. The driver acks it, at once and before any write, with 0062 or 9997. It decodes the result and writes it to `Result`, one `UA_Server_writeDataValue` per field ([`server.h:460`](https://github.com/open62541/open62541/blob/v1.5.9/include/open62541/server.h#L460)), `TighteningId` last, the whole result in one post to the server's thread (*Address space*). Every field of one result carries the same source timestamp, and no server timestamp: open62541 answers a read's and a sample's with its own clock ([`ua_services_attribute.c:323`](https://github.com/open62541/open62541/blob/v1.5.10/src/server/ua_services_attribute.c#L323)). The counters follow, then the event (*Events*).

The source timestamp is the result's own time. The wire gives `YYYY-MM-DD:HH:MM:SS`, local to the controller, with no zone and no fraction ([Table 108][op]). The driver reads it in the row's `timeZone`, an hour that comes twice as the pass nearer its receipt, since a result comes seconds after it is made and the passes are an hour apart, and a result with no time is sourced at its receipt. A result whose time is not after the last result written for the row gets the last time plus a millisecond, so the row's source timestamps are distinct and increasing, and a clock set back further than `maxSkew` is warned of once; `Result.Time` holds the controller's own. Two rundowns inside one second keep their order and are two records; after a break, the historian refuses a value sourced earlier than the last it stored for a node ([`Group.cpp:400`](../../libs/historian/src/Group.cpp#L400)).

The controller's clock is the controller's. At each connect, the driver reads it with MID 0080 and sets `_Op.Skew`, and warns past `maxSkew`, five minutes. The driver does not correct the skew, since a clock the plant has set wrong is the plant's to set right (*Open questions* #5).

**Backfill.** The specification's recovery for a network failure is MID 0064, an old result by tightening id, id 0 being the latest ([§5.8.5, Table 121][op]); nothing is pushed again on its own. On a PF6000 the ids are global across virtual stations and not consecutive. So the appendix's procedure walks back: ask for id 0, then for the id received less one, which answers the result before it, until a known id comes back, dropping each result whose station id, MID 0065 revision 7's, is not the connection's, MID 0002 revision 6's ([PF6000 appendix][pf6kapp] §2.4).

When the link returns, the driver:
1. subscribes to results first, and holds and acks what arrives;
2. walks back by that procedure once the clock's reply has come, from the oldest held id less one, the appendix's start for a known id, or from id 0 when nothing is held, until it reaches the last tightening id it wrote, or a lower id timed no later than the last time it wrote, whichever station made it, or a MID 0004, or `maxBackfill` requests, 2 000, or id 1, which has nothing before it;
3. writes what it found, oldest first, then the held results, each tightening id once whichever way it came, a result that came both ways as it was pushed. A found result is a MID 0065, which carries no limits, no parameter set name and no time of its last change ([§5.8.6][op]), so each `Result` variable it lacks is written with the result's source timestamp and `Bad_NotSupported`, where it does not read so already, the next live result writing it Good, and its event leaves it out (plan review #5).

The ids run up, a controller's stations sharing them. So a result of a higher id than the last written is later whatever its time, a second rundown in the last one's second or one made after a clock was set back. A lower id timed after the last write belongs to a run of ids that began again, and is written by its time. A found result names its station at revision 7 alone, so below it every result is taken for the connection's. Its time is read in the row's zone as a pushed result's is, but for an hour that comes twice: that is the later pass where it is not after the result made after it, since a found result is read long after it was made.

Short of the last id, at a MID 0004, at `maxBackfill` requests, at id 1 or at a reply with no id, it adds the gap's unknown size as one to `_Op.LostResults` and warns, naming the last id it has and the oldest it reached. A link lost during the walk writes nothing of it: what was found and held is still the controller's, and the next connection walks again from the latest.

Until a result has been written in a run there is no last id, and a result whose tightening id is 0, which MID 0064 reads as the latest, gives none. Without a last id nothing is filled: not on a row's first connection, and not on a link that returns before the row's first result. Nor is anything filled after a gateway restart, which is the gap every source's collection has across a restart (*Open questions* #6).

A fill is a burst of writes inside one publishing interval of the collector's subscription, 500 ms ([`HistGroupHost.h:90`](../../apps/OpcGateway/src/hist/HistGroupHost.h#L90)). So the Open Protocol driver raises its server's `queueSizeLimits` maximum ([`server.h:2303`](https://github.com/open62541/open62541/blob/v1.5.9/include/open62541/server.h#L2303)) to the larger of open62541's 100 and twice `maxBackfill`, the walk's bound plus as many held, since the held count is not known when the config is fixed, and a fill reaches the collector's queue whole (plan review #8).

**Commands.** These are methods on `Commands`, each the MID of the same purpose ([§4.5][op]):
- `SelectPset( pset: UInt16 )`, MID 0018, 000 to 999;
- `SelectJob( job: UInt16 )`, MID 0038 at 2, 0000 to 9999, or at 1, 00 to 99 (plan review #11);
- `DisableTool()` and `EnableTool()`, MIDs 0042 and 0043 at revision 1, every tool of the connection;
- `DownloadVin( vin: String )`, MID 0050, 25 characters at most.

The rights come first, from the Call service, which asks `getUserExecutableOnObject` before it runs a method; the library's `UAAccess` answers it, and `getUserExecutable`, from the host's `INodeAccess` (plan review #1). A method's callback runs on the server's thread under the service lock. A value that fits no revision the row may ask, as the codec measures it, is refused there, `Bad_OutOfRange`, before anything is sent and whatever the link. Else the callback has the host hold the call, posts the request to the row's strand, and returns `Good_CompletesAsynchronously`. The strand sends the request behind whatever is outstanding and answers through `UA_Server_setAsyncCallMethodResult` ([`server.h:1417`](https://github.com/open62541/open62541/blob/v1.5.9/include/open62541/server.h#L1417)), in a post to the server's thread:
- Good on MID 0005;
- `Bad_InvalidState` on MID 0004, with the code and its name in `_Op.LastError` and the log, a Viewer's 92 and a second Actor's 35 among them;
- `Bad_Timeout` where the controller leaves the request unanswered for `replyTimeout`, which is the link's loss too;
- `Bad_NoCommunication` while the link is down, where it goes while the request waits, and on a row whose controller the driver refused;
- `Bad_OutOfRange` where the revision the controller settled does not carry the value, a job past 99 at MID 0038's revision 1, with nothing sent at it;
- `Bad_Shutdown` where the driver's stop finds the call waiting. The request out at the stop keeps its answer.

The server's `asyncOperationTimeout` for a call is `callTimeout`, 30 s, past the reply deadline and the queue. A pending call is kept by the host, keyed by the output pointer the server handed it and a number, since the pointer of a cancelled call may key the next while the cancelled one's answer is still to come. `asyncOperationCancelCallback` ([`server.h:2255`](https://github.com/open62541/open62541/blob/v1.5.9/include/open62541/server.h#L2255)) erases the entry, as the PLCs spec's host does for its reads, so a reply that finds none logs and drops. The cancel is the timeout's, a client's Cancel's, the queue's limit's and the shutdown's; a session's close cancels nothing, so a call outlives its session: it is sent, its answer logged, and the result dropped where no session remains. A call cancelled before the strand has it, as one past `maxAsyncOperations` is once its callback returns, is not sent: its client has been told it was refused. The request reaches the strand through the server's thread, after the service and its cancel. One cancelled once the strand has it is sent, and its answer is logged and not set.

Rights resolve through `HistHost`'s live groups, read when the Call service asks, as the servers plan's 3a map ([#383](https://github.com/Jde-cpp/opc-hub/issues/383)) is fed from them; the host keeps no map of its own, since a gateway may run with no endpoint to keep 3a's. A method of the row's namespace resolves to the groups on the row's connection that hold a variable, one member at least. A call needs Execute ([`usings.h:33`](../../include/jde/access/usings.h#L33)), the right the vocabulary keeps for methods (clients spec *Open questions* #9), on the enforced row of one of those groups, through `Authorize::ScopedRights`, the criteria overload the endpoint uses, a lookup and never `Gate` under the service lock. A row that no group holds refuses commands; so does a group whose row is unenforced or grants no Execute, and so does a gateway with no historian, which has no live group. A method of the server's own, namespace 0's, is called by no one. The refusal is the Call service's `Bad_UserAccessDenied`, before anything is sent, with the user, the method and the message #237 gave history edits in the log at Information, since a Call result carries a status only (*Open questions* #10); a method's UserExecutable attribute reads the same answer beforehand. Every call is logged at Information with the hub user, the method, its arguments and the answer.

**Events.** `TighteningResultEventType` is a subtype of BaseEventType in the row's namespace, at `s=TighteningResultEventType`, with a property per `Result` variable, under the variable's name and of its type, each optional. Each result written raises one, whatever its result type, through `UA_Server_createEventEx` ([`server.h:1616`](https://github.com/open62541/open62541/blob/v1.5.9/include/open62541/server.h#L1616)), in the result's post behind its writes, with:
- SourceNode `Result`, whose EventNotifier has SubscribeToEvents;
- Time the result's source timestamp, and ReceiveTime the gateway's clock as the event is raised;
- Severity 100 for OK and 500 for anything else;
- Message `OK` or `NOK`, with the parameter set, `OK, parameter set 3`, and `No status` for the first word where the result sent no tightening status;
- a field for each variable the result wrote a value to, under the variable's name in the row's namespace, `2:Torque` in a client's select list. A variable the result has no value for, one its revision does not carry, one a found result lacks (*Backfill*) or one it sent blank, is an empty field.

No object of the type is made: the fields go with the event, each under the key open62541 looks its select clause up by, the base fields among them, since a clause it does not find there it looks for by parsing every key it was given (the plan's Phase 9 *Built*). A fill raises its events in one burst; an event item's queue is its client's ask, 100 for the gateway's own, and one a fill overflows says so in its stream.

The Server object emits every event ([`ua_subscription_event.c:1630`](https://github.com/open62541/open62541/blob/v1.5.9/src/server/ua_subscription_event.c#L1630)), so a client subscribed there sees them too. Events are on in this build: `UA_ENABLE_SUBSCRIPTIONS_EVENTS` defaults on ([`CMakeLists.txt:116`](https://github.com/open62541/open62541/blob/v1.5.9/CMakeLists.txt#L116)) and the superbuild leaves it ([`build/CMakeLists.txt:477`](../../build/CMakeLists.txt#L477)); alarms and conditions are off.

An event is one result whole, where the variables arrive as separate items. It is the clients spec's Events tab ([#424](https://github.com/Jde-cpp/opc-hub/issues/424)) that shows them, and the historian keeps none. OPC 40450-1 delivers results this way too, as a `Result` field of an abstract `JoiningSystemResultReadyEventType` ([OPC 40450-1 §8.1][ijt-events]). This type is not that one (*Open questions* #3, #4).

**Sessions and rights.** These are the PLCs spec's (its *Sessions and rights*), by group, the servers spec's endpoint model. A web user comes by issued token and the collector by the process's certificate under the own-certificate rule. Browse and reads are open to every session, as #237 ships `nodeIds`. Nothing is writable, so the PLCs spec's write rule has nothing to govern here. Its place is taken by the command rule above, which keys on the same groups with Execute in place of Update.

The OpcServer's per-tag acls are not offered, for the PLCs spec's reasons. The provider the gateway creates per connection ([`UM.cpp:42`](../../apps/OpcGateway/src/auth/UM.cpp#L42)) is an identity provider and plays no part.

**Groups, history and the endpoint.** Nothing changes for the collector. The servers spec's endpoint serves a driver row's members under the row's own URI, `urn:jde:<slug>:open-protocol`, which its namespace rule keeps as it is, being already prefixed with the slug ([`../servers/spec.md`](../servers/spec.md) *Namespaces*; the PLCs plan's 0.4 in [#383](https://github.com/Jde-cpp/opc-hub/issues/383)). **OEE.** A station is a machine of the OEE spec over a group that holds `Counters.Total`, `Counters.Ok` and `Counters.Nok` as its Total, Good and Reject signals ([`../oee/spec.md`](../oee/spec.md) *Counts*). The counters count since the driver started and restart at zero with the driver, at a gateway start or a row edit (*The row*), which the engine reads as a reset and counts whole. Without a State signal, the station runs while results arrive and stops once the machine's `idleTimeout` passes without one (OEE spec *State*).

At revision 3 and above, a counter counts a result of result type 1, a tightening ([§5.8.2][op]), or of no type, so a loosening, a batch increment or a bypass counts for nothing; below revision 3, every result counts. `Ok` and `Nok` count by the tightening status (*Open questions* #13), and a counter is written when it moves.

**Controllers.** The supported ones:
- **PF4000.** One connection per controller, on 4545.
- **PF6000 and PF8.** A row per virtual station on that station's port, opened in the controller's firewall ([PF6000 manual][pf6k34]). The PF6000 appendix's ceilings are 0001 at 6, the parameter set selection, 0014 to 0018, at 1, 0061 and 0064 at 8, the alarms at 3, 0042, 0043 and 0050 at 1, the VIN subscription at 2, 0034 to 0037 at 4 and 0038 at 2, with multi-spindle results unsupported ([PF6000 appendix][pf6kapp], Table 1, release 2.8). On a PF6000 MID 0018 selects by the *Identifier number* of the station's *Source Tightening* task, and is refused with code 3 where the station runs none, while MID 0015 and a result carry the set's index in the tightening menu, so `Selected.Pset` after a `SelectPset` need not be the number sent; MID 0038 takes a *Source Batch* with numbers, and is refused with code 20 without one (§2.5, §2.7).
- **Other vendors.** Desoutter's CVI3 takes a port per tightening unit and Cleco a port per tool ([Tulip][tulip]), and Stanley, Ingersoll Rand, Bosch Rexroth and Kolver controllers speak the protocol with their own MID tables. A row per port works for all of them, with the step-down and the row's ceilings for their differences, untested until a site has one.

Not in this spec:
- **MT Focus 6000.** It implements neither 0061 nor 0042 and 0043, and sends results only as MID 1201 and 1202 ([MT Focus 6000][mtf], pp. 35–36).
- **PowerMACS.** Its results are its own MIDs.

`testConnection` names the system type either reports from MID 0002 revision 5, and the driver refuses either until the MID 1201 piece (*Later*): its session stops, with the reason in `_Op.LastError` and the log, and is not opened again until the row changes or the gateway starts.

**Tests.** `Jde.Opc.Tests` runs a test controller in-process on the library's controller side, on 4645, the live port plus 100 as the suite's other ports are ([`Opc.Tests.jsonnet:37`](../../apps/OpcGateway/tests/config/Opc.Tests.jsonnet#L37)), with a driver row against it under a `/gateway/drivers.portBase` of 4980, past the hub suite's 4975 and 4976; the hub suite's own case takes 5170 and a controller on 4745. The fixture shares the driver's codec, so the suite proves the two sides agree, not that either agrees with a controller. The codec's own cases therefore decode messages built from the specification's tables, field by field. Conformance is checked by hand against Jarrekstar's open-protocol-device-simulator, Rust under Apache 2.0 or MIT, which, at the commit the plan's 0.3 pins, serves the session, parameter sets, jobs, the VIN, tool control and MID 0061 at revisions 1 to 7, 998 and 999 to several clients, each MID family at the revision its profile selects, or at any it implements, revision 1 until set, with code 97 for the rest ([github][sim]; the plan's *Phase 0*, 0.3's *Built*), and against a controller (*Open questions* #12, #15). The simulator's check is four cases of `Jde.Opc.Tests`, `DriverSimulatorTests`, skipped unless `/testing/openProtocolSimulator` names its ports: the step-down, MID 0061 at each of its seven revisions, the five commands and a group recording a run, each driving the simulator through its HTTP API. Where its frames are not the tables', its MID 0002 from revision 4 and the revision its acknowledgements carry, they are the library's cases, as it wrote them (the plan's *Phase 10*, 10a's *Built*). The simulator has no MID 0064, no alarms, no MID 0080 and no link-level acknowledgement, so backfill, the alarms, link level, the skew and the Disconnect action are the controller's check alone. That check is ready ahead of the controller (the plan's *Phase 10*, 10b's *Prepared*): a bench client that speaks the protocol raw and reads it by the tables, a mode a check, among them the ones the driver cannot make of itself, an acknowledgement withheld and a sequence number out of order; four cases of `Jde.Opc.Tests`, `DriverControllerTests`, skipped unless `/testing/openProtocolController` names the controller's two stations, which ask on the console for the hand at it; and the hub, for the Disconnect action and the soak. Until the controller is there each runs against a stand-in for it, two of the library's test controllers as a PF6000's two stations by its appendix, so a pass says the check works and nothing of the controller. Frames captured from the controller go under the library's `tests/fixtures/`, where `FixtureTests` reads each.

The cases:
- The codec round-trips each MID the driver speaks, decodes the specification's example frames, blank header fields and all, and refuses a length past 9999, a short field, a mixed digit field and a missing NUL; a fuzz target runs over the decoder.
- The session steps MID 0001 down from 6 to a fixture that answers 97 above 3, and reads a MID 0002 at 3 answered to a MID 0001 at 6, and 0061 pushes at 3 to a 0060 at 7, by their headers. It takes link level when MID 0002 revision 6 says so and application acks when not, re-acknowledges and drops a repeated sequence number, and reconnects on any other out of order. It keeps alive past a fixture that drops at 15 s of silence, and treats a reply past `replyTimeout` as a lost link.
- `testConnection` reports the fixture's identity.
- A result of each revision, 1 to 7, lands in `Result` with its fields, in the row's zone. Two in one second get distinct, increasing timestamps; a field outside the settled revision reads `Bad_NotSupported`; the counters count tightenings and skip a loosening.
- A group over `Result.TighteningId`, `Result.Torque` and `Counters.Ok` with no `MinTimeInterval` records every one of a burst faster than the publishing interval. With a `MinTimeInterval`, it keeps the last result per interval. A processed read agrees with the QL.
- Backfill: the link drops, both stations make results, and the driver fills only its own, in order, before the held live one; a result pushed between the subscribe and the first MID 0064 is written and counted once. A `maxBackfill` too short sets `LostResults`. A group over the row records the filled results with their own timestamps.
- `Selected` and `Alarm` follow their pushes, go `Bad_NoCommunication` with the link, and recover.
- Each command, called through the QL's `call` on a user's client, sends its MID, answering Good on 0005, `Bad_InvalidState` on 0004 and `Bad_Timeout` on silence. It refuses on an ungrouped row and on an unenforced group, and passes with Execute on an enforced one. A shutdown with a call pending leaves no entry.
- A result raises an event heard at `Result` and at the Server object with its fields, its time, its severity and its message, through the socket's `SubscribeEvents` on a user's client, the clients spec's Events ([#424](https://github.com/Jde-cpp/opc-hub/issues/424)) having landed (plan review #2). A NOK is at 500, an event leaves out what its result lacks, and a fill raises one per result written.
- The driver server's certificate is refused when the anchor is withheld, the suite's list being its own certs directory ([`Opc.Tests.jsonnet:76`](../../apps/OpcGateway/tests/config/Opc.Tests.jsonnet#L76)), and the collector's session opens as the gateway's user.

The emulator's tests add a station that makes one result in a cycle.

**Limits.** The `/gateway/drivers` block:

```jsonnet
gateway:{
	drivers:{
		portBase:: 4870, //a driver row's server listens on 127.0.0.1 at portBase + its row id, every kind; the tests take 4980, the hub's 5170
		openProtocol:{
			keepAlive:: "PT10S", //MID 9999 after this long without a message either way; a controller drops a link silent for 15 s
			replyTimeout:: "PT10S", //a request, an ack or a command unanswered this long is a lost link
			callTimeout:: "PT30S", maxAsyncOperations:: 0, //how long a method call holds, the server's asyncOperationTimeout; and its async queue, maxAsyncOperationQueueSize, 0 unlimited as open62541's
			reconnectMin:: "PT1S", //the backoff between connection attempts, doubling to reconnectMax
			reconnectMax:: "PT1M",
			maxBackfill:: 2000, //MID 0064 requests one recovery may send; twice it is the deepest queue the row's server gives an item, where that is past open62541's 100
			maxSkew:: "PT5M", //the controller's clock against the gateway's, past which each connect warns
			log:: false //every frame in and out at Trace under the OpenProtocol tag
		}
	}
}
```

The PLCs spec's `/gateway/plc.portBase` is this block's `portBase` when it un-parks, its other keys a `drivers.plc` block.

**Later.**
- MID 1201 and 1202, the operation results the MT Focus 6000 and newer firmware send, and their replay from an index or a time on subscribe ([Table 151][op]), which would make backfill a subscription option.
- Multi-spindle results, MID 0100 and 0101.
- Trace curves, MID 0900 and 0901, as arrays.
- The selected parameter set's data, MID 0012 and 0013, as properties.
- Batch size and reset, MID 0019 and 0020.
- Alarm acknowledge, MID 0078, and alarms as conditions once a condition object exists (clients spec, [#425](https://github.com/Jde-cpp/opc-hub/issues/425)).
- Inputs and relays, MID 0200 to 0225.
- Backfill across a gateway restart, from a last id kept on disk.
- TLS, which the specification allows ([§2.1.1][op]).
- The controller dialing the gateway, the specification's second connection scenario ([§3.3.1][op]).
- OPC 40450-1's address space, served beside this one or instead of it (*Open questions* #3).
- EngineeringUnits on the torques from `TorqueUnit`.
- The gateway setting a controller's clock, MID 0082.

**Out of scope.**
- Downloading or editing tightening programs and parameter sets, MID 2500 to 2506, or anything else a controller's own tool, ToolsTalk, owns: its ports, its firewall, its Disconnect action.
- The serial transports, STX and ETX framing and 3964R ([§2.1.2][op]).
- ToolsNet or any vendor collector as a dependency.

## Open questions

All fifteen ruled 2026-10-21, each as recommended; the plan is [`plan.md`](plan.md).

1. **The shape.** The PLCs spec ruled the shape (its *Open questions* #1, #2 and #9): a driver behind an embedded UA server per row, inside the gateway, on loopback, at `portBase` plus the row's id. That spec is parked, not withdrawn, and its reasons hold here: `UAClient` is `final` with no interface ([`UAClient.h:32`](../../apps/OpcGateway/src/UAClient.h#L32)), and every operation is an await through it. Recommended: take the ruling as standing, with the host made kind-agnostic so the Allen-Bradley driver and Modbus sit on it later. Ruled 2026-10-21: as recommended.
2. **The row's fields.** One json `driver` column, which each kind's save rule validates, against typed columns per kind, which the PLCs spec added (`plc`, `path`, `tag_list`) and which would grow with every family. Recommended: `driver`, with the PLCs spec's three as its members when it un-parks. Typed columns give the schema's own checks and a QL filter; neither matters for fields only the driver reads. Ruled 2026-10-21: as recommended.
3. **The address space.** Our own flat model against OPC 40450-1's. The companion specification's smallest claim, the IJT Result Server Facet, makes result events mandatory, each result one ExtensionObject field, and makes the result variable optional ([OPC 40450-1 §11.2.2.2][ijt-facet]). It needs DI, AMB, IA, Machinery and Machinery Result loaded, and its types compiled into open62541, which the superbuild does not do, or loaded at run time by a nodeset loader the gateway does not link ([`../servers/spec.md`](../servers/spec.md) *The server library*). A group cannot collect an event. Recommended: our own model now, with the variables a group collects and an event of our own; OPC 40450-1 later, when a client asks for it by name. Ruled 2026-10-21: as recommended.
4. **Values and events.** Each result as variables, which groups, history, the endpoint and OEE take, and as an event, which carries it whole to the Events tab and to clients that expect results as events. The alternatives are variables only, or events only, the companion specification's way, which the historian cannot store. Recommended: both, the event as its own small piece after the variables. Ruled 2026-10-21: as recommended.
5. **Timestamps.** The controller's time, read in the row's zone, nudged to stay distinct and increasing, with the gateway's receipt as server time. The alternative is the gateway's receipt as source time, which is right to the millisecond for a live result and wrong by the outage for a backfilled one. Recommended: the controller's time, with `_Op.Skew` and the warning, the clock left to the plant. Ruled 2026-10-21: as recommended.
6. **Backfill.** Within a run, by the MID 0064 walk, bounded, against none at all, as no other source of the gateway backfills. Across a gateway restart, from a last id on disk, is the third option. A controller keeps its results, up to 100 000 on a PF8 ([PF8 manual][pf8]), and DeMeter calls traceability lost without the recovery ([DeMeter][demeter]). Recommended: within a run now, across restarts later. Ruled 2026-10-21: as recommended.
7. **Acknowledgement.** Link level with sequence numbers where MID 0002 revision 6 says the controller supports it, and application acks otherwise. The alternative is application acks everywhere, which every controller answers. Recommended: link level where offered; the specification all but requires it ([§3.2][op]). Ruled 2026-10-21: as recommended.
8. **Revisions.** Step down per MID from the highest the driver decodes on codes 74, 76 and 97, under the row's ceilings, as node-open-protocol and Desoutter's DeMeter do. The alternative is Kepware's: fixed revisions per row that the user sets ([Kepware][kep], pp. 12–13). Recommended: step down, with the ceilings for a controller that answers a revision badly. Ruled 2026-10-21: as recommended.
9. **MID 0061's range.** Revisions 1 to 7, against 1 to 12 plus 998's stages and 999's light form. Seven is what the simulator serves; the PF6000's ceiling is 8; Kepware stops at 5. Recommended: 1 to 7, the rest later, a controller above 7 answering 7 since every revision below the highest is implemented ([§1.4][op]). Ruled 2026-10-21: as recommended.
10. **The command right.** Execute on an enforced row of a group that holds one of the row's variables, the group model's answer for a method, which belongs to no node a group holds. The alternatives are Update by the same route, which the PLCs spec's writes take, and Administer on `serverConnections`, which makes every command an admin's. Recommended: Execute by group. A command changes what the line does next, and the group is who runs the station. Ruled 2026-10-21: as recommended.
11. **The command set.** Five methods: parameter set, job, tool disable and enable, VIN. The alternative adds batch size and reset, alarm acknowledge and job restart now. Recommended: the five, the rest later; these are the ones a line's MES sends. Ruled 2026-10-21: as recommended.
12. **The test controller.** In-process, on our own codec, with the specification's tables as the codec's oracle and Jarrekstar's simulator and a controller as hand checks. The alternative spawns that simulator in the suite, which brings a Rust toolchain to both runners and a dependency on a project with one author. Recommended: our own. Ruled 2026-10-21: as recommended.
13. **Counters.** Kept by the driver since it started, counting tightenings by result type. The alternative is the controller's batch counter, which resets per batch and per parameter set, so is no running count. Recommended: the driver's counters. Ruled 2026-10-21: as recommended.
14. **The MT Focus 6000.** Out until the MID 1201 piece, the driver refusing its system type, against MID 1201 in this spec. It implements no MID 0061 and sends only 1201 and 1202, a second result decode in the variable-field pattern ([§2.4][op]). Recommended: later. Ruled 2026-10-21: as recommended.
15. **Hardware.** Nothing here is verified against a controller. The step-down, link level, the PF6000's walk and station filter, whether a subscription answers the current state at once, and what a controller does with results while a 0062 is outstanding are the specification's and the appendices' account, or unknown. Recommended: the plan names a bench controller, a PF6000 with two virtual stations, for the hand checks; until then, the suite's coverage is the fixture's. Ruled 2026-10-21: as recommended.
